## Not confirmed

What the reader looked for and could not settle from the code; each item is an open question for the epic that needs it.

- **JDK behaviour**: that `new java.util.Random()` is seeded from `System.nanoTime()` XOR a static uniquifier, and that HotSpot identity hashes vary between JVM launches, are properties of the JDK, not of this repository; I did not read JDK sources here. The repository only shows that no seed is passed (Random.java:44, 48) and that `Actor`, `Mob`, and `Class` keys rely on default `hashCode` (no `int hashCode` override under `actors/`, `levels/`, `items/`).
- **How often actor-order ties occur** in practice (equal `time` and equal `actPriority`): the mechanism is confirmed (Actor.java:255-265) but not its frequency; a harness determinism test is needed.
- **Whether the audio completion callback can fire during levelgen** in the desktop backend (Music.java:190-201 is invoked from a libGDX completion listener); the code path exists, the timing is platform-dependent.
- **Save/load round trips**: I did not verify that every seeded consumer (e.g. `MossyClump.shuffles`, `cat.dropped`) is bundled so that a resumed game continues the same seeded sequence; only `Generator.storeInBundle` (Generator.java:899-951) was read.
- **`Level.java:1383-1434` mob loops**: iterate `mobs` (HashSet) but I did not check whether they draw random numbers per mob; listed here as a potential, not confirmed, order dependency.
