Technique 1 of 3

First Principles: the descent

Five lenses, one per floor, each dug down to what must be true. The deeper the floor, the closer to bedrock.

depth1
WINNINGWhat does winning mean?
16

First Principles Thinking, first lens

  1. canonical number = win rate on default settings per class over a fixed public seed set (the Elo of Shatterfish)
  2. relative strength chain like Stockfish: no absolute rating, each version measured against the previous by SPRT; publish the chain
  3. before any wins exist, the metric is the survival curve over depth (Kaplan-Meier); compare brains by curve dominance
  4. boss staircase: Goo, Tengu, DM-300, Dwarf King, Yog kill rates as the natural curriculum and milestone metrics
  5. per-class ladder: Warrior first; winning means all four classes above threshold, reported separately
  6. ascension rate (amulet back to surface) as the long-horizon north star; challenges (up to 9) as the far horizon
  7. in-game score as a continuous auxiliary target with less variance than binary win; never the headline
  8. solved-seed set: per-seed boolean "can the bot win this seed"; the set must grow monotonically and doubles as a regression suite
  9. strength at fixed compute budget, like chess time controls: bullet/blitz/classical think budgets, strength published per budget
  10. headroom metric: oracle-assisted upper bound per seed (measurement only, never play) shows how much is left to gain
  11. comprehension for overlay users: a run where every decision has a stated reason a human can follow
  12. the number is meaningless without parity proof; publish win rate together with the fairness test status
  13. calibrate against published human win rates (Evan's blog, in-game stats) as a milestone; tier-3 lore until sourced
  14. winning is not turns per second; speed is a rig property, not a brain property
  15. process definition: no merge without SPRT-backed improvement; winning is the culture, not a number
  16. "beats the median human on default" as the public headline milestone; "wins on 9 challenges" as the legend milestone
depth2
AUDIENCEWho is the overlay for?
11

First Principles: overlay audience

  1. v1 = the developer debugging the bot; the overlay is the debugger for everything after it
  2. learners: coach mode where the bot only advises (ghost cursor, "I would do X because Y") and the human plays
  3. autoexplore-with-brains: human plays, hands boring stretches to the bot (DCSS auto-explore with judgement); the most useful daily feature
  4. speedrunners and seed hunters: bot as route verifier for a seed; run N then scrub the replay
  5. streamers: spectator layout with big text so chat can read the reasoning live
  6. researchers: export run logs, compare brains, plug in a new brain without touching the overlay
  7. balance testers: the rig shows how a mechanics change shifts win rates (we never propose upstream, but the tool exists)
  8. accessibility tangent: decision narration as text is a screen-reader-friendly view of a run
  9. decisiondeveloper first (E5), learner/coach second (E8), spectator and researcher exports later
  10. coach mode contract: explanations use game vocabulary from the Codex (item and mob names as the game shows them), never internal jargon
  11. the overlay can never become a cheat tool because it shows only what the Observation holds; oracle draws a red border
depth3
TRUSTWhat makes the rig trustworthy?
13

First Principles: rig trustworthiness

  1. every published number ships with (tag, seed set, commit, brain config, SPRT params) and the exact command that reproduces it
  2. seed sets are public fixed files: smoke, standard, and a holdout set never run during development to prevent seed overfitting
  3. pre-registration: SPRT hypotheses and bounds fixed before the run; the results file carries a hypothesis id; the rig refuses unregistered comparisons
  4. hash-chained run logs: Observation hash and action per turn; replay verifies; tampering is evident
  5. baselines reproduced by CI on GitHub runners, not the author's laptop
  6. fairness tests on every PR; a badge derived from them in the README
  7. report confidence intervals and run counts, never point estimates; publish failed tests too, like Fishtest
  8. methodology page: why SPRT, the Bernoulli win model, depth as ordinal, power analysis, caveats such as partial seeding
  9. cheat detector: run the same brain on two hidden-state variants of one visible world; decisions must be identical until observations diverge
  10. nightly replay of a random published run from its log; mismatch fails the night
  11. challenge the bot: anyone submits a seed, the rig runs it, the result is published
  12. numbers are tied to the upstream tag; an upgrade re-baselines and publishes the delta
  13. depth is a higher-power metric than win rate while win rate is near zero; say so and use it early
depth4
SEARCHWhat does fairness do to search?
13

First Principles: fairness and search

  1. search sees Observation plus beliefs only; hidden state is sampled from beliefs (redetermination) before every rollout
  2. belief model is a first-class fairness object: Beliefs.update(Observation) is a pure function with its own leak tests
  3. tension resolved: brain cannot import game code and cannot reimplement rules, so the harness offers an engine-backed fair simulator that runs the real engine on redetermined reconstructions
  4. reconstruction option A: build a Level and mobs from the Observation plus a belief sample (world builder)
  5. reconstruction option B: snapshot the real save (Bundle) and scrub hidden information by re-sampling it; fair only if scrubbing is complete, so it needs differential tests
  6. search leak test: replace the true hidden state with random alternates; decisions must be identical because search only sees beliefs
  7. strategy fusion pitfall: averaging over determinizations pretends the hidden info will be known later; limit horizon or use information-set search
  8. MVP for E6 is one-ply lookahead over Codex tactical tables (expected damage, hit chance by level difference, speeds); no simulation needed
  9. budget rollouts to visible-enemy turns and boss fights; scripted policy handles quiet turns
  10. turns-to-live heuristic from Codex expected damage per visible enemy; cheap and fair
  11. thread confinement as enforcement: Observer and ActionExecutor assert they run on the render thread; the brain thread can never touch game objects
  12. learned eval (E9) trained on oracle labels is fair as long as inputs are Observations and training seeds are disjoint from evaluation seeds
  13. danger map per cell from visible enemies' Codex stats, drawn in the overlay
depth5
STALLWhere does the program stall?
13

First Principles: stall risks

  1. headless boot dies on static rendering touchpoints (GameScene, Sample, GLog, Camera); first E1 story audits every touchpoint reachable from game logic
  2. snapshot/restore of static singletons is the tar pit; abstract model first, engine rollouts later with criteria
  3. threading: the game is not thread-safe; only immutable Observations cross to the brain thread
  4. upstream churn: 4.0.0-beta already exists; pin, get an E3 baseline, then upgrade once by procedure
  5. hooks multiply; cap at a handful and review each
  6. rig too slow to matter; measure throughput in E1 (1,000 runs in seconds) before building on it
  7. SPRT futility while win rate is near zero; use depth and boss milestones early
  8. overfitting to the standard seed set; holdout set
  9. determinism breaks through HashMap order, time, or threads; determinism test on every PR
  10. human bandwidth at checkpoints; bmad-loop for unattended stories once psmux is installed
  11. scope creep into overlay polish and learned eval; the ideas ledger
  12. motivation gap before the first amulet; celebrate and publish the first Goo, first Tengu
  13. LLM context drift across sessions; ADRs, handoffs, fairness reviewer, retrospectives feeding CLAUDE.md

Technique 2 of 3

Mind Mapping: the map of the dungeon

Seven branches radiate from the engine. Hover a leaf for the full line; the lists below carry every idea verbatim.

ENGINE 6 ideas

  1. Observation schema versioned; hash is SHA-256 of a canonical serialization
  2. Observation history per run enables belief debugging and time travel in the replay
  3. classloader isolation: load core in a separate classloader per worker to run N games in one JVM despite static singletons
  4. throughput NFR stated with arithmetic: 1,000 runs x 2,000 turns = 2M turns; at 10k turns/s that is 200 s
  5. validActions(obs) exposed by the harness; fair because the UI shows what is possible
  6. stubs for GLog and Sample via hooks guarded by a headless flag

BRAIN 7 ideas

  1. layered: reflex (scripted), tactical (search), strategic (playbooks), meta (item-ID, upgrade allocation)
  2. goal stack shown in the overlay: explore, loot, descend, with the reason for the top goal
  3. fear map: per-cell danger from visible enemies
  4. item-ID as value of information versus risk; safeTest is the risk side
  5. playbooks as data files editable by experts, versioned, rig-tested; the openings book analogy
  6. eval as weighted features (HP fraction, food, depth progress, known items, threat) tuned by SPSA on the rig, straight from Stockfish tuning
  7. class-specific layers over a shared core; Warrior first

RIG 6 ideas

  1. seed sets smoke (20), standard (1,000), holdout (1,000), bosses (early boss variety)
  2. cause-of-death taxonomy from Codex classes; heat map by depth
  3. death replay gallery: worst deaths auto-published with their decision logs; a bug source
  4. distributed workers via GitHub Actions matrix, free for public repositories, like Fishtest workers
  5. two-stage tests like Fishtest STC/LTC: short seed set first, long set to confirm
  6. solved-seed regression suite must stay won on every merge

OVERLAY 7 ideas

  1. docked native panel, collapsible, respects the UI scale setting
  2. explain view as a small decision tree of top alternatives with scores
  3. pause-on conditions as a tiny rule language: hp<30%, new-enemy, before:read, floor:boss
  4. replay scrubber over JSONL with the belief state at each turn
  5. ghost path on the map for the plan; considered cells dimmed
  6. "why not X": click an action, the brain scores and explains it
  7. hotkeys through KeyBindings and SPDAction if the hook stays small

COMMUNITY 4 ideas

  1. public leaderboard of brain versions on the standard set
  2. bot-vs-seed challenge issues
  3. a post per epic on the docs site telling the numbers as a story
  4. low-code contribution path: playbook PRs with rig numbers

KNOWLEDGE 3 ideas

  1. Codex diff across tags is an automatic mechanics changelog
  2. numeric lore claims auto-checked against the Codex
  3. glossary consistency check between code identifiers and docs

PROCESS 1 idea

  1. bmad-loop for unattended stories after E1; fairness reviewer on every brain PR; retrospective per epic feeds CLAUDE.md

Cross-cutting insights

Two plaques the coach nailed up after the three techniques, before converging.

The one architecture fork

the fairness rule plus "no second rules implementation" forces search to go through an engine-backed fair simulator or Codex-derived tables; this is the central architecture decision for E6 and needs its own ADR with criteria

Ordinal metrics from day one

depth-based metrics and boss milestones carry the program until win rate is measurable; the rig must support ordinal metrics from day one

Synthesis

Three of the five questions have the same answer: measurement.

Three of the five questions have the same answer, measurement. Winning is a measured ladder, trust is measurement made verifiable, and stall risk is mostly measurement arriving too late (win rate near zero) or too slow (throughput). The fairness question is the one genuine architecture fork: Codex tables now, engine-backed redetermined simulation later, decided by an ADR with criteria. The audience question is settled by sequencing, not by choice: developer, then learner. Recommended directions D1-D5; Checkpoint B asks the product owner which to keep.
