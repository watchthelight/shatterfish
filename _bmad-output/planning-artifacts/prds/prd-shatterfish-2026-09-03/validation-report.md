## Overall verdict

This is a real PRD with a thesis, not a backlog with headings: information parity and measurement are stated as disciplines, every feature group serves one of them, the Non-goals do work, the counter-metrics are product-specific, and the Glossary is good enough that the architecture and epics workflows can source-extract from it. What is at risk is done-ness at the rungs the program actually gates on. The E4 rung (FR-31, SM-3) has no number behind "large majority", the Composite outcome the Sequential test optimizes rewards exactly the diving behavior SM-C2 says is worse, and the determinism contract (FR-2) does not say whether a process may host more than one Run, which is the question the E1 classloader spike and the Rig runner both hang on. Fix those three and the PRD is ready for the architecture workflow; the rest is medium-weight hygiene the epics workflow would otherwise have to invent.

The isolated adversarial reviewer (session 9, run against v1-final after the rubric findings were applied) materially widened the picture: 1 critical, 14 high, 27 medium, 12 low. Its verdict was "not as-is". It found three side doors around Rule 1 that no listed test covered (Codex data generated by running `core` reaching the Brain outside the Observer, the valid-Action set as an unhashed leak channel, and seed memorisation through E9 training labels and the developer's own edit-and-rerun loop on public seeds), a PAUSED-versus-HUMAN contradiction that made the Overlay's Modes undefinable, a Composite outcome that still rewarded dive-and-die in the pre-win era, a Sequential test with no per-pair statistic to build on, a Panel with no state machine, FRs whose consequences belonged to other epics, and game-reality gaps (killing Yog-Dzhewa is not the Win, Score scales with challenge flags, cross-Run profile state makes Overlay Runs unreplayable). Its own summary: "Every problem below is fixable with a sentence or a table; none needs a rewrite."

This report grades the PRD as it was reviewed (v1 and v1-final): the grade is Poor because the adversarial review returned a critical finding, and the Done-ness clarity dimension was thin. PRD v2 (`version: 2` in its frontmatter) has since applied every rubric high and medium, the adversarial critical, all fourteen adversarial highs, and most adversarial mediums; each finding below carries a Status line recording whether v2 fixed it, partially fixed it, or left it open. ### High (17)

**[Rubric] Decision-readiness** — Composite outcome contradicts SM-C2 (§ 3 Glossary "Composite outcome"; § 7 SM-C2)  
The Glossary orders the per-Run result "win, then depth reached, then turns survived", so among losses a deeper, faster death ranks above a shallower, longer one. SM-C2 says "A Brain that dives and dies deeper is worse" and offers "the Composite outcome and the survival curve" as the corrective, but the Composite outcome is the thing that rewards diving. The Sequential test (FR-21) optimizes this ordering, so the Rig will accept Brains that dive.  
Fix: decide the ordering on purpose and say what was given up. Options: (a) keep depth-first and reword SM-C2 to "depth reached alone, outside the Composite outcome"; (b) rank losses by a survival-weighted measure (depth with a turns floor, or the boss staircase) and note the cost in test power; (c) make the ordering a pre-registered parameter of the Hypothesis ID. Record the choice in the E3 statistics ADR.  
Status: fixed in v1

**[Rubric] Done-ness clarity** — "Large majority" is the E4 exit condition and has no number (§ 4.5 FR-31; § 7 SM-3; addendum epic map E4)  
FR-31 requires Policies "sufficient to kill Goo on a large majority of the `standard` Seed set" and SM-3 repeats the phrase. E4's done-when is therefore unfalsifiable; the epics workflow cannot write the closing story.  
Fix: state a fraction with a confidence interval (for example "Goo killed on at least 60% of `standard` at 95% confidence, per class where the class is implemented") or, if the owner will not commit before data, make it a `[NOTE FOR PM]` with a placeholder and the moment it is set (the first `standard` run of the random Baseline in E3 is the natural one).  
Status: fixed in v1

**[Rubric] Done-ness clarity** — FR-2 does not say whether a process may run more than one Run (§ 4.1 FR-2; § 4.4 FR-19; § 6.2; § 8 NFR-3)  
FR-19 says "One process per Run by default", NFR-3 and FR-5 measure "Runs per minute for one process", and section 6.2 calls classloader isolation "a spike in E1, not a requirement; processes are the default". These agree only if a process hosts exactly one Run, which JVM and libGDX startup makes expensive at 1,000 Runs. If a process hosts Runs sequentially, SPD's static state (`Dungeon`, statistics, journal, RNG) must be reset between Runs and FR-2's "identical Observation hashes" must hold regardless of what ran before in the same process. The PRD does not say which, and the architecture workflow will have to guess.  
Fix: add a Consequence to FR-2: "A Run's Observations are independent of any Run previously executed in the same process" or "The Harness executes at most one Run per process and the Rig's throughput figures include process start". Then make FR-19 and NFR-3 agree with the choice.
