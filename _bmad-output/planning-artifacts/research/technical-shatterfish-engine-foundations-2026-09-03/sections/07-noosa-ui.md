## 7. Noosa and SPD UI patterns for a docked panel

**Question.** Which native building blocks exist for an in-game docked panel, how do forks add HUD elements, what are the threading and input rules, and how is UI scale handled? All claims below were verified against the pinned tag v3.3.8 by reading the source; a first pass on upstream `master` (post-beta) found the same code.

**Scale and layout.** The UI draws through `PixelScene.uiCamera`, a fullscreen camera at `defaultZoom`; `defaultZoom` is read from the saved `SPDSettings.scale()` and only falls back to `gate(2, ceil(density x scaleFactor), maxDefaultZoom)` (scaleFactor 3.75 for the full desktop interface, 2.5 mobile) when the saved value is out of range, and in full UI it is raised to at least half the maximum [93]. World zoom (`minZoom`, `maxZoom`) is separate, so a panel sized in UI pixels is unaffected by the player zooming the dungeon [93]. There is no layout manager: every `Component` positions its children in `layout()` from `Game.width/height`, and `PixelScene.align()` snaps to `1/defaultZoom` to keep nine-patches and text crisp [107, 93]. Text comes from `renderTextBlock(text, size)`, which also folds in the device's real pixel scale [93]. `SPDSettings.interfaceSize()` is 0 (mobile), 1 (full layout without the inventory pane) or 2 (full with it), default 2 on desktop and forced to 0 below the full-UI minimum of 360 x 200 UI pixels [106, 93].

**Building blocks and reserved space.** `Chrome.Type` offers sixteen nine-patch skins from one atlas; `TOAST_TR` and `TOAST_TR_HEAVY` are the translucent HUD backgrounds, `WINDOW` (margin 6) the modal frame, `RED_BUTTON`/`GREY_BUTTON` the buttons [94]. `GameScene.create()` builds the world groups in fixed z-order and then the HUD: `MenuPane` (width 31), `StatusPane` (height 39 in full UI), `BossHealthBar`, the resume/action/loot/attack indicators, `GameLog`, `Toolbar` (height 26), and, only at interface size 2, `InventoryPane` (187 x 82) docked bottom-right with the toolbar lifted above it [95, 105]. `layoutTags()` stacks the indicator tags upward from the toolbar on the left or right per `flipTags()` and sizes the `GameLog` to 160 UI pixels wide in full UI [95]. A right-docked panel therefore competes with the menu pane at the top right and the inventory pane at the bottom right; the free column is between them, or the panel replaces the inventory pane at interface size 1. `ScrollPane` clips with its own camera and already handles drag, wheel, and keyboard scrolling, which makes it the scrolling-log widget [104].

**Threading.** Rendering runs on the libGDX thread: `Game.render()` draws then steps, `update()` caps the frame delta at 0.2 s, and `Game.runOnRenderThread` is literally `Gdx.app.postRunnable` [96]. Game logic runs on a dedicated "SHPD Actor Thread": `Actor.process()` picks the next actor under `synchronized (Actor.class)`, waits on a `Char`'s sprite while it `isMoving`, and parks with `wait()` when nothing can act; `GameScene.update()` spawns that thread when nothing is processing and `notify()`s it at most sixty times a second, drains a `toDestroy` list so UI removed from the actor thread is freed on the render thread, and `onPause()` waits up to 500 ms for the actor thread before saving [97, 95]. The input seam is exact: when `Hero.act()` finds no `curAction` it calls `ready()`, which sets `ready = true` and `GameScene.ready()`, and returns false so the actor thread parks; the default cell listener then runs `if (hero.handle(cell)) hero.next()` [98, 95]. `Hero.interrupt()` clears the action and `GameScene.cancel()` clears resting [98]. Text is the trap: `RenderedText.measure()` throws "Text measured from the actor thread" if called from the actor thread, and `RenderedTextBlock.text()` is not synchronized even though `build()` is, so panel text must be set on the render thread [103, 102]. The two consequences for the overlay: the actor waiting on `sprite.isMoving` means a bot that drives the hero inside the real game runs at animation speed unless it also controls sprites, and every panel update must be posted to the render thread.

**Input.** Actions are `SPDAction` constants in a static `defaultBindings` map keyed by libGDX key codes with a parallel controller map; bindings load from and save to `keybinds.dat` as deltas from the defaults [99]. `KeyBindings` exposes `setAllBindings` and lookups but no `addKeyBinding`; registering a new action means adding the constant and its default binding, after which the settings window lists it automatically because it enumerates `GameAction.allActions()` [100, 101]. That is a small, contained hook.

**Forks.** No fork with a large in-engine docked panel was found. The one "overlay" fork does its big HUD as an external Godot companion app over an HTTP gateway and adds only small Noosa widgets in-game [108]. Every mod is a full-source fork, so the invasive edit of `GameScene.create()` is the norm. On stability: `GameScene.java` and `ui/` did not change between v3.3.7 and v3.3.8, and the `4.0.0-beta` tag is the v3.3.8 commit, so the hook surface is stable until 4.0 stable lands [109].

**Verdict.** The panel is a `Component` with `Chrome.TOAST_TR` background, `renderTextBlock` text, `RedButton` controls and a `ScrollPane` log, added at the end of `GameScene.create()` and positioned in `layoutTags()`'s free column; hotkeys are one `SPDAction` constant each. Two hooks are required (adding the panel in `GameScene.create()`/`layoutTags()`, and the `SPDAction` constants) plus one more if the embedded driver must bypass sprite waits for speed. All panel writes go through `Game.runOnRenderThread`; nothing on the brain thread may touch a `RenderedTextBlock`.

**Confidence.** High throughout: every claim cites the pinned tag by line.
