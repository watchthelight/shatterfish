## 1. libGDX headless backend

**Question.** Can Shattered Pixel Dungeon's core be driven on libGDX's headless backend without a scene, what breaks, and how can many games run per machine?

**What the backend is.** `HeadlessApplication` was contributed as a mocked backend for servers sharing client logic; its `MockGraphics` header says as much [35]. Its constructor loads natives, installs a logger, creates real `HeadlessFiles` and `HeadlessNet` and mock graphics, audio, and input, assigns the process-global `Gdx.app/files/net/audio/graphics/input`, and starts a dedicated main-loop thread; it never assigns `Gdx.gl`, and every GL getter on `MockGraphics` returns null [34, 35]. `HeadlessApplicationConfiguration` has three fields; `updatesPerSecond` of 0 gives a busy loop with no sleep (maximum throughput) and a negative value means `render()` is never called, so a harness would drive the game itself through posted runnables [36]. `exit()` is asynchronous: it posts a runnable that ends the loop on the next iteration [34].

**What breaks.** Anything that constructs a `Texture`, `SpriteBatch`, or `ShaderProgram` dereferences `Gdx.gl` and throws; issue #3383 (2015) records it and is closed without a fix, and master still returns null GL, so this is by design and permanent [42]. Issue #5995 (2020) lists the two community workarounds: Mockito-mocking `Gdx.gl`, which breaks once code needs real return values such as shader compile status, or a hidden LWJGL3 window with a real context [43]. A 2020 server write-up hit the same NPE from a map loader that auto-created textures and fixed it with a stub image resolver [44]. The community test skeleton boots a `HeadlessApplication` and mocks `GL20` [45]. No published hand-written no-op `GL20` was found in three rounds. Preferences work but write real files under `preferencesDirectory`, so parallel instances sharing one directory would collide [40]; audio calls are safe no-ops [41]; `Timer` is JVM-global and rebinds to whichever `Gdx.files` is current, so it churns and mis-pauses when several applications share a JVM [39].

**Natives.** The constructor calls `HeadlessNativesLoader.load()` first, which delegates to `GdxNativesLoader.load()`; that method has a `disableNativesLoading` flag and otherwise lets any failure propagate [38, 34]. The failure is eager and concrete: the lead reproduced it this run on Windows 11 with libGDX 1.14.0, where constructing a `HeadlessApplication` without `gdx-platform:natives-desktop` on the classpath threw `SharedLibraryLoadRuntimeException: Couldn't load shared library 'gdx64.dll'` with cause "Unable to read file for extraction", and adding the natives as a runtime dependency fixed it [52]. The loader source itself has moved out of the main repository (gdx-jnigen) and was not retrieved, so the exception path is verified empirically, not from source.

**Many games per machine.** Every `HeadlessApplication` overwrites the same `Gdx.*` statics, which libGDX's own javadoc calls "a design faux pas" it accepted deliberately [37]; the wiki says no libGDX class is thread-safe unless marked and that all listener methods run on one thread, and nowhere addresses multiple applications [51]. The LWJGL3 backend's multi-window support does not help: `newWindow` shares one `Gdx.app`, one loop, and the first window's GL context [50]. Consequence: parallel instances mean separate JVM processes, or one classloader per instance so that each loader has its own `Gdx` class; the latter is mechanically feasible for a headless loop (a plain thread with no GL affinity) but has no precedent or maintainer statement and must be spiked. SPD's own statics (`Dungeon`, `Actor`, `Game`) sit on top of libGDX's and impose the same constraint.

**Versions and health.** Releases: 1.13.1 (2025-01-08), 1.13.5 (2025-05-13, the Sonatype Central migration), 1.14.0 (2025-10-19), 1.14.1 (2026-05-18), 1.14.2 (2026-06-05), confirmed by both the GitHub tags and the libgdx.com posts [47, 46]. libGDX has been built with JDK 17 since 1.13.0 while its published jars target Java 7 (core, headless) and Java 8 (LWJGL3); LWJGL 3.3.3 has been pinned since 1.13.1, with 3.4.x needed only on Java 25+ [48, 49]. gdx-liftoff recommends JDK 21 and targets 1.14.2 [49]. No release note in the trailing year touches the headless backend: it is stable by neglect, which is acceptable for a mock backend whose surface has not changed.

**Verdict (amended after the red-team pass; see Contrary evidence).** The headless backend is the right substrate for E1, but "never construct a scene" is not viable: at the pinned tag, attack, zap, throw and operate actions resolve inside sprite-animation callbacks that only a scene update fires, and there are 969 sprite dereferences in game logic [130, 126]. The plan becomes a **headless scene**: a harness-owned scene that supplies the Groups sprites need, a no-op `GL20` installed before any texture class loads, real atlases decoded through `Pixmap` (no GL), the desktop natives shipped, `updatesPerSecond = 0`, a per-instance preferences directory, and a driver that fast-forwards `scene.update()` with a large elapsed time until the actor thread parks. Upstream edits are then limited to the few static helpers that assume a `GameScene`. Parallelism is per process by default; classloader isolation must keep libGDX in a shared parent loader because of the JNI one-loader rule, and is an E1 spike with a measured throughput number as its exit criterion.

**Confidence.** High on backend behaviour (source read on master, matching the 1.14 line SPD uses); high on the natives failure (first-hand reproduction); high on the sprite-coupling finding (verified line by line at v3.3.8); medium on the "no no-op GL exists" absence claim; low on classloader isolation, which is inference without precedent.
