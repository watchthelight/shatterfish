### Q3 — GL20 stubs and Lwjgl3Application.newWindow

- CLAIM: `Lwjgl3Application` constructor sets process-global statics `Gdx.app = this; Gdx.audio = audio; this.files = Gdx.files = createFiles(); this.net = Gdx.net = new Lwjgl3Net(config);`. `newWindow(ApplicationListener, Lwjgl3WindowConfiguration)` copies the app config, then `return createWindow(appConfig, listener, windows.get(0).getWindowHandle());` — every extra window shares the first window's GL context and is appended to the single `final Array<Lwjgl3Window> windows` field via `postRunnable(...)`. The main `loop()` iterates `for (Lwjgl3Window window : windows)` and runs while `running && windows.size > 0`. ## Contradictions

- LWJGL version for released 1.14.x: the CHANGES fetch attributed "Update to LWJGL 3.4.3" to 1.14.0, 1.14.2 and 1.14.3 simultaneously (summariser artefact). Against it: (a) the gdx-liftoff README says LWJGL3 >= 3.4.0 is needed for Java 25+ and that liftoff enforces it "using Gradle constraints" — unnecessary if libGDX 1.14.2 already pulled 3.4.3; (b) a search snippet says 1.14.2 uses LWJGL 3.3.3 unless overridden; (c) the 1.14.1/1.14.2 news post has no LWJGL bump line. Best reading: released 1.13.1–1.14.2 = LWJGL 3.3.3; master/1.14.3 = 3.4.3. Needs one direct read of the CHANGES lines to settle.
- Java baseline wording: "built using Java 17" (JDK needed to compile libGDX / run liftoff) vs. "-PjavaVersion default Java 7, LWJGL3 backend Java 8" (bytecode target of published jars). Not a true contradiction, but easily conflated; for a bot harness the relevant fact is that the published gdx / gdx-backend-headless jars are old-bytecode while the tooling wants JDK 17+ (liftoff: 17–26, 21 recommended for Construo packaging).
- Release dates: the news post for 1.14.1 & 1.14.2 is dated 2026-05-28, between the brief's 2026-05-18 (1.14.1) and 2026-06-05 (1.14.2). Blog date != Maven date.

- GL20 stub: GitHub code search for `implements GL20` outside libgdx-org repos; check crykn/guacamole for a MockGL20-style class. For the Shatterfish harness, a hand-written no-op `GL20`/`GL30` returning plausible values (e.g. `glCreateShader` non-zero, `glGetShaderiv` compile success) is the standard practice the issues above imply is necessary.
- Per-instance isolation: given Lwjgl3Application.newWindow shares Gdx.app/loop, and HeadlessApplication also writes the same `Gdx.*` statics, "many instances per machine" should mean separate JVM processes (or separate classloaders per instance — untested lead), not multiple HeadlessApplication objects in one JVM.
