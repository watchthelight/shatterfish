# Red team: headless HeadlessApplication harness for Shattered Pixel Dungeon

Scope: attack the claim that SPD (libGDX 1.14) can be driven headlessly for thousands of runs by booting `HeadlessApplication`, never building a scene, driving `Actor.process()` directly, stubbing "a handful" of static rendering touchpoints (GameScene, Sample, GLog), one JVM per instance, later classloader isolation, thousands of turns/s per process. Sources below were retrieved this run; nothing is asserted from memory.

## Counter-evidence

- FINDING: The actor loop itself blocks on sprite animation state. `Actor.process()` contains `if (acting instanceof Char && ((Char) acting).sprite != null) { synchronized (((Char)acting).sprite) { if (((Char)acting).sprite.isMoving) { ((Char) acting).sprite.wait(); } } }` and the loop condition is gated on `!Game.switchingScene()`. The only place `isMoving` is cleared and the waiter released is `CharSprite.onComplete(Tweener)`: `synchronized (this) { isMoving = false; ... ch.onMotionComplete(); GameScene.sortMobSprites(); notifyAll(); }`, which runs from the scene's update pass. With no scene updating tweeners, any Char that has a non-null sprite parks the actor thread forever. The `sprite != null` guard means the harness must guarantee that no Char ever gets a sprite, not merely that GameScene is stubbed. | SOURCE: https://raw.githubusercontent.com/00-Evan/shattered-pixel-dungeon/master/core/src/main/java/com/shatteredpixel/shatteredpixeldungeon/actors/Actor.java and https://raw.githubusercontent.com/00-Evan/shattered-pixel-dungeon/master/core/src/main/java/com/shatteredpixel/shatteredpixeldungeon/sprites/CharSprite.java | PUBLISHER: 00-Evan/shattered-pixel-dungeon (GitHub, master) | PUB_DATE: retrieved 2026-09-03 | STRENGTH: strong
- FINDING: Game-logic resolution is driven by animation completion callbacks, not by the actor loop. `CharSprite.attack(int cell, Callback callback)` stores the callback and plays the attack animation; `onComplete(Animation anim)` then calls `executing.call()` or, with no custom callback, `ch.onAttackComplete()` / `ch.onOperateComplete()`. Hero.java confirms `onAttackComplete()` exists and touches `AttackIndicator.target(...)`. So the Hero's melee attack, zap, and operate actions only resolve (damage applied, turn spent) when an animation finishes on the render side. A headless harness cannot just "not construct a scene"; it must re-route every `sprite.attack/zap/operate(...)` call site to invoke the callback synchronously, which is a semantic rewrite of the turn pipeline rather than a stub. | SOURCE: https://raw.githubusercontent.com/00-Evan/shattered-pixel-dungeon/master/core/src/main/java/com/shatteredpixel/shatteredpixeldungeon/sprites/CharSprite.java | PUBLISHER: 00-Evan/shattered-pixel-dungeon (GitHub, master) | PUB_DATE: retrieved 2026-09-03 | STRENGTH: strong

- FINDING: Per-instance classloader isolation inside one JVM collides with the JNI rule that a native library may be bound to only one classloader per process. ## Strongest argument the conclusion is wrong

The conclusion treats rendering as a layer that sits on top of game logic and can be left unconstructed. The upstream code says the opposite: rendering is in the critical path of turn resolution. `Actor.process()` parks the actor thread on `sprite.wait()` whenever a Char has a sprite that is moving, and that wait is only released by `CharSprite.onComplete(Tweener)` running from the scene's update pass. Hero melee, wand zaps and item operations do not resolve in `act()`; they resolve in `CharSprite.onComplete(Animation)` via `ch.onAttackComplete()` / `ch.onOperateComplete()` / the stored `animCallback`. Hero.java alone has 68 unguarded sprite/UI/GameScene/Sample/Emitter calls threaded through `act()`, `ready()`, `move()`, `damage()`, `die()`, `search()`. So the two viable headless strategies are both expensive: (a) keep every sprite null, which means auditing and guarding hundreds of `sprite.` dereferences across Hero, Mob subclasses, items, wands, buffs and blobs, and rewriting every animation-callback site to fire synchronously; or (b) keep sprites alive as Noosa objects and drive a fake update loop, which drags in `Gdx.gl`/`Gdx.graphics`, TextureFilm, Emitter and BitmapText, all null under `HeadlessApplication` (libgdx #5995), and inherits the render/actor lock-ordering hazards documented in SPD #431. Either way the honest estimate is a maintained fork with a pervasive `headless` flag, not "guarding a handful of static touchpoints", and every upstream merge will reintroduce unguarded sites. The classloader-isolation follow-up is further undermined by JNI's one-classloader-per-native rule, meaning the "later optimization" needs a shared-parent native loader that re-couples instances through the same `Gdx` statics. The throughput target itself is plausible in principle (Hadronize shows ~400k turns/s for a tiny JS engine), but that number is irrelevant if the actor thread deadlocks on the first `sprite.wait()` or the harness spends its time in a per-decision policy bridge. Six-month regret scenario: a bespoke SPD fork that diverges from upstream, is validated by turn-count rather than by parity with the real game (because animation-driven ordering was replaced with synchronous ordering, changing when effects apply relative to `spend()`), and whose "headless" results are quietly not the game players play.
