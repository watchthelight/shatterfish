## Goal

Epic 1 makes Shattered Pixel Dungeon run without a window, a graphics driver or a human, so that the same Run tuple produces the same Run twice and so that everything the bot will ever see arrives through one class that shows it only what the screen shows. It is the foundation of every number Shatterfish will publish; nothing after it is trustworthy if it is wrong. The epic is done when a seeded Warrior Run completes headlessly, the same tuple run in two separate JVMs yields identical Observation hashes at every Input wait, the whole fairness suite is green on the pull-request gate, and the measured throughput and tactics properties are published.

## Requirements & Constraints

**Non-negotiables binding every story.** Information parity is the only rule of play: the bot may use only what a human at the same screen could have (what the renderer draws, the game log, the journal, general game knowledge), never an unidentified item's true identity, an unseen enemy's position, hidden traps or secret doors, RNG state or the seed; mind vision, magic mapping and the like count only while the in-game effect is active. This is enforced by architecture, not intentions: `brain` cannot import game code (the build fails if it tries), a single class named `Observer` is the only door from game state to the bot, and every change to `Observer` ships with leak tests. Oracle mode exists only for debugging and training labels, is off by default, visibly flagged, and can never be enabled in a ranked rig run. Every edit to an upstream file is a hook: minimal, justified, marked at the site, labelled `touches-upstream`, with a row in `docs/UPSTREAM.md` in the same pull request; prefer new modules over edits; the v1 budget is ten rows and exceeding it requires an ADR. Everything is Java, in-process, in one JVM: no second implementation of the game's rules in any language, no bot process over a socket. Every Run is fully determined by its tuple. Any UI is the game's own toolkit; nothing in this epic draws, and no Swing, JavaFX, ImGui or web view may enter through it. Any claim about game mechanics is settled by reading the pinned code and citing `path:line`, never from memory or a forum; ask the `upstream-reader` subagent. Issues track state, story files carry content, docs carry knowledge; no TODO in code without an issue number. Keep upstream's licence and attribution and never file Shatterfish bugs upstream.

**What the epic must deliver, testably.**
- A Run of a given class, challenge flags and seed starts in a fresh Profile with no window, no OpenGL context and no Android SDK, and runs to completion, including turn paths that resolve inside sprite callbacks; boot without the desktop natives fails with a message naming them.
- Two Runs with the same tuple give identical Observation hashes at every Input wait, independent of wall-clock time, thread scheduling, hash-map iteration order and Profile contents; the determinism test spans two JVMs and runs on every pull request.
- The Observer builds only from what the game computes for drawing, the game log, this-Run journal notes and the open Prompt, never from raw model fields; the Observation is immutable, serializable and content-hashed, equal exactly when hashes are equal, and carries the valid-Action set so the leak tests cover it.
- The ActionExecutor applies every Action through the paths the UI uses, rejects an invalid Action with a reason before touching state, and a completeness test maps every hero-affecting input to an Action kind or documents it as unsupported.
- A random valid-action agent completes 1,000 seeded Warrior Runs unattended; a Run ends in death, a Win, or the 20,000-turn cap recorded as a loss with cause `turn cap`.
- Leak tests prove that an unidentified item, a mob behind a wall, a secret door, a hidden trap, an invisible enemy, the seed and the RNG state are absent from a constructed world's serialized Observation; two worlds identical to the player but different in hidden state serialize byte-identically; mind vision, blindness and magic mapping change the Observation exactly as they change the screen; without the launcher flag no code path carries true identities or unseen positions into anything the Brain can hold; `Observer` and the executor assert their owning thread and fail fast. The whole suite runs on every pull request.
- Snapshot, restore and redetermination ship as reserved interfaces plus a restore-and-replay test; the rollout host and the scrubber are E6.
- No throughput rate is promised before it is measured; the published page names the machine, tag, commit and reproducing command.

**Cross-cutting rules.** Windows and Linux are supported (Linux on the PR gate, Windows nightly from E3); macOS is best effort. No Shatterfish module opens a network connection, and the ArchUnit ban on `java.net` applies to every module, not only `brain` and `api`. Run logs and results pages are plain text. Docs and ADRs change in the same pull request as the code; a new docs page needs a `mkdocs.yml` nav entry because the docs build is strict; generated files are never hand-edited. Any diff near `Observer`, `ActionExecutor`, `brain` or the `api` schema carries the `fairness` label and passes the `fairness-reviewer` subagent before the PR opens. Every story names the test class that proves it; test classes end in `Test`, leak tests in `LeakTest`.

## Technical Decisions

- **Module graph and stack.** `api` depends on the JDK only; `harness` on `core` and `api`; `codex` on `core` and `api`; `brain` on `api` only and may not use `java.io`, `java.nio.file`, `java.net` or `java.lang.reflect`, so the Observation is its only channel; `rig` on `harness` and `brain`; `overlay` on `core`, `harness` and `brain`. Enforced by declared edges, a resolution-time classpath check and ArchUnit 1.5.0. Java 21 for Shatterfish modules, Gradle 9.4 wrapper, libGDX 1.14.0 headless backend with desktop natives, JUnit 5.
- **Layout.** `org.shatterfish.api` holds the `Observation` record tree, sealed `Action`, `Decision`, the opaque versioned `Belief`, `SnapshotHandle`, `Simulator`, `ObservationCodec` and `JsonWriter`. `org.shatterfish.harness` holds `Observer`, `OracleObserver`, `ActionExecutor`, `RngControl`, `Profile`, `Snapshot` (never leaves the module), `SnapshotStore` and `Redeterminer`; `harness.scene` the headless scene, no-op GL and Pixmap atlases; `harness.driver` the driver contract later shared by the embedded and replay drivers; `harness.agent` the random agent and benchmark, a harness tool rather than a Brain, so `brain` stays empty in E1. The fairness suite lives under `harness/src/test`; `Hooks.java` under `core` is the one upstream-side class.
- **Headless scene and loop.** The harness owns a scene that creates the same groups, sprites and emote icons the real scene creates, so actor-thread random draws match an Overlay Run; the no-op GL binding is installed before any texture class initialises. The driver thread owns the loop, fast-forwards scene updates and drains the posted-runnable queue itself; no library loop thread exists; a Run that never reaches a wait fails with a diagnostic naming the last actor rather than hanging. After the scene story, no story adds a guard to actor or item code.
- **The Input wait is the unit of everything.** An Input wait is "hero ready and either no window or a recognised Prompt window", detected by the notification hook at the observe site in the hero's act method and confirmed by the driver, never polled and never taken from the hero's ready call, which fires on every actor wake-up. Exactly one Observation, Decision, Action, Run-log record and reseed happen per wait; the 0-based long index `k` is the primary key across all of them; the per-wait order is increment `k`, reseed, observe, decide, execute, record. A move is one step to an adjacent cell because the game never returns the hero to ready between cells.
- **Observation and codec.** A whitelist by construction: every field is something the screen, HUD, log or journal shows, and enums have no secret members. The canonical binary codec in `api` is the only encoder (fixed field order, big-endian integers, length-prefixed strings, no floats, canonical list order); SHA-256 over section hashes plus the version is the whole hash. The header carries the schema version, the Codex version, the sealed flag and the oracle flag, and never the seed, the salt, a turn counter or oracle data; the JSON rendering carries the hash and is never parsed back. The Belief is a separate opaque value that `harness` may only hash, log and hand back.
- **Observer rules.** Reads the game's drawing predicates only and never recomputes visibility; the visibility whitelist is a per-rule table where each row cites the renderer's line and names its leak test, and a checklist test keeps every row covered. It runs only at an Input wait on the UI-role thread, owns the game-log listener and re-registers it on every scene creation because the game replaces it. Oracle data is a sidecar view behind a launcher flag; the oracle flag sits in the hashed header so oracle hashes differ from fair ones, and the Brain-facing type has no path to the sidecar.
- **Actions and executor.** A closed sealed kind list; one Action is one human input; every parameter is a value the Observation carries; the valid set is computed from the Observation alone; `Wait` is invalid while a Prompt is open. The executor dispatches exactly what a click, key or button would, drives the game's own selector for a targeted Action within the same wait, re-validates before any state changes, rejects with a `Reason` value rather than an exception, and is the only Shatterfish caller of the hero's input and next-turn methods.
- **Determinism.** The Run tuple is (tag, class, challenges, seed, salt, Action list); the salt is drawn by the runner at execution, logged, and never observed. The base generator is reseeded from `mix(salt, k)` at every wait, after the game's own initialisation has finished resetting the generator stack; the mix function has a published test vector. Every Run gets a fresh versioned Profile (English, intro off, guide pages read, no remains, rankings or badges) in its own working directory, and a different Profile version is refused. One process hosts one Run; classloader isolation was a spike, not a requirement. Identity-hash iteration order is removed by the identity-order hook row, and Shatterfish code never lets `HashMap` or `HashSet` order decide an outcome. The cross-platform hash comparison belongs to the nightly rig, not this epic.
- **Threads.** The game's actor thread is never touched by Shatterfish code; the UI-role thread (the driver thread headless, the render thread in the Overlay) is the only one that observes and executes; the brain worker holds only an immutable Observation. `Observer` and `ActionExecutor` assert the UI-role thread on entry; no Shatterfish code takes a monitor on a game type.
- **Hooks.** A hook site is one line calling a nullable listener field in `Hooks.java` (or a semantically neutral one-line edit) carrying the marker `// shatterfish-hook:<id>`; a test counts markers against the rows of `docs/UPSTREAM.md`. Rows are named by the reviewer's question, not by file, as corrected after the touchpoint audit. The rows this epic spends: the registry, the scene seam, read-only accessors for private state the screen shows, letting the actor loop run with no game scene (the null guards plus the Input-wait notification), and identity-order removal. The sprite-wait bypass, draw routing, the PAUSED input gate and action registration are E5's rows and must not be spent here.
- **Snapshot.** Built over the game's own save bundles and module-private to `harness`, because bundle bytes in `api` could be inflated into hidden state by anything holding them; `api` carries only an opaque handle and the simulator interface; the belief-sample and redeterminer interfaces exist without implementations, and a handle whose scrubbed flag is false is refused by contract.
- **Conventions.** `api` values are Java records; Shatterfish code logs through `java.util.logging` with the module as logger name and never re-logs game log lines; a Run id is `<tag>-<class>-<challenges>-<seedcode>-<salt>-<brain>`; times never enter hashed data; `--oracle` exists only on the launcher. The binding detail lives in the accepted decision records under `docs/adr/` (schema and hashing, visibility rules, RNG seeding, hook guarding and the corrected ledger, snapshot and redetermination, threading, the Action schema and executor contract, the headless scene and Input-wait detection) and in the cited rules pages under `docs/rules/`; open the record each story names before starting it.

## UX & Interaction Patterns

The Overlay is E5, but its contract shapes what this epic must not preclude. The stepping unit everywhere is one Input wait, so the driver contract must let a caller advance exactly one wait, and a Decision is tagged with its `k` so a stale one is never executed. Oracle marking in the Overlay (a red border and an `ORACLE` label) and the rig's refusal of oracle Runs are both driven by the oracle flag this epic puts in the Observation header and the Run log. Human turns will later be recorded with actor `human`, and an input the Action set cannot express ends replay-verifiability from that wait, which is why the executor's completeness test must list unsupported inputs with a reason. Hand-back re-plans from the current Observation, so nothing in the harness may assume the previous Decision was executed.

## Cross-Story Dependencies

- The stories are in dependency order and none depends on a later one: the schema precedes the Observer that fills it, the Observer precedes the Action set computed from it, the Action set precedes the executor and the random agent that draws from it, and the determinism, fairness, oracle, thread and snapshot stories build on the finished loop.
- The per-wait sequence lands with wait detection, with the reseed stubbed until the salt story and the record stubbed until the rig's Run log (E3). The Observation's actions section is declared with the schema but is populated only once the sealed Action type and the valid-set function exist.
- Every hook row landing in this epic needs its `docs/UPSTREAM.md` row in the same pull request.
- The header's Codex-version field predates the Codex (E2); the story that fills it decides what it holds until then, and the same field later appears in the Run-log header and the Registration.
- Handed to later epics: the rig's refusal of oracle Runs (E3, the parallel runner); the cross-platform hash comparison (E3, the nightly replay job); the throughput benchmark with a Brain attached (E4); the rollout host, the scrubber and any tactical search (E6); the PAUSED input gate, sprite-wait bypass, draw routing and key-binding hooks (E5).
- The throughput and Run-length numbers published at the end of this epic feed the rig's seed-set sizes and parallelism (E3) and the tactical-search decision (E6); the leaf-correlation and disambiguation measurement is a research session in its own right, separate from the throughput benchmark.
