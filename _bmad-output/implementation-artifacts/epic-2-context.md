# Epic 2 Context: Codex

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 2 turns the pinned upstream source into the bot's general game knowledge: every mob, item, generator weight, guarantee schedule, spawn table, trap, recipe, level structure, player-facing string, asset path and changelog entry, generated by one Gradle task into a tag-named folder, cited to `path:line`, and unable to drift from the tag it describes because CI regenerates it and fails on any difference. The Codex is what lets the Brain know the game the way a wiki-reading human does, without a second implementation of the rules and without a second door into hidden state: it is static, seed-free data about types and tables, never about a Run. The epic also delivers the vanilla-versus-Shattered vocabulary diff the lore pipeline will need and the citation checker the upgrade procedure depends on. It is done when one task regenerates `codex/<tag>/` and CI fails on drift.

## Stories

- Story 2.1: The generator skeleton and the seed-free guarantee
- Story 2.2: Mobs and spawn tables by depth
- Story 2.3: Items, generator weights, decks and guarantees
- Story 2.4: Item guarantees, tier tables and limited drops
- Story 2.5: Measured combat tables

- Story 2.8: The vanilla-versus-Shattered vocabulary diff
- Story 2.9: The drift check and the generated documentation
- Story 2.10: The citation checker

## Requirements & Constraints

**Non-negotiables binding every story.** Information parity still governs: the Codex describes types and tables, never a Run, so no generated value may derive from the seed, a Profile or any Run state, and the Codex leak test proving that joins the fairness suite on every pull request. Any claim about game mechanics is settled by reading the pinned code and citing `path:line`, never from memory or a forum; ask the `upstream-reader` subagent. No second implementation of the game's rules in any language: the generator reads the real engine and, for combat, runs it. Every edit to an upstream file is a hook with a `docs/UPSTREAM.md` row in the same pull request; the generator is expected to need none, since it reads the game through reflection and the game's own methods, and a hook spent here comes out of the ten-row budget. Docs and ADRs change in the same pull request as the code; generated files are never hand-edited; no TODO in code without an issue number. A pull request touching the Codex generator gets an adversarial fairness review.

**What the epic must deliver, testably.**
- One build task regenerates the Codex into a tag-named folder and the generated documentation pages; consumers read the tag they need.
- Coverage is enumerated, not asserted: a completeness test checks every concrete mob, item, trap, recipe and room class against the game's own class lists, and boss stats carry their Stronger Bosses variants.
- Generation is parameterised by depth and challenge flags wherever the game's tables are: spawn rotation including the rare-mob, rare-alternate and champion rules; guarantee schedules with their challenge-flag variation; tier tables by depth region.
- Seed-free: generating twice with different seeds and different Profiles gives byte-identical output; generating with a live Run in progress equals generating from a cold start.
- Combat behaviour enters as measured tables, never transcribed formulas: the generator sweeps the engine's own hit and damage methods over a parameter grid and records outcomes with the measured method's `path:line` and the grid swept; the tables are reproducible across runs and across the two supported platforms; no combat formula is written by hand anywhere in `codex` or `brain`.
- The dumped guarantee schedules must reproduce the game's own decisions over a swept range of depths and counter states, including the rule that armour picks its class by tier index rather than by category weights, and the special and secret room solution items so a floor's guarantees are derivable.
- Every generated entry carries a `path:line` citation into the tag.
- CI regenerates the Codex and fails if the committed output differs, naming the first differing file; a deliberate edit to a committed file is verified once to fail CI.
- The vocabulary diff lists names present in one game only and names present in both whose mechanics differ, each row citing both sources; it has no consumer until E7 and is marked as the variant classifier's input.
- The citation checker reports any `path:line` citation in `docs/` that no longer resolves at the pinned tag, runs in CI, is wired into the upgrade procedure's re-verification step, and passes the existing rules pages unchanged.
- The generated documentation pages build under strict mode, so every new page needs a `mkdocs.yml` nav entry.

**Cross-cutting rules.** No Shatterfish module opens a network connection; the vanilla Pixel Dungeon source is read only and never built into the product. Windows and Linux are supported; the cross-platform vehicle for the combat-table stability assertion does not yet exist in CI (the Windows job is planned for the nightly rig workflow from E3), so the story that needs it must either create one or state what it asserts on the PR gate alone. Every story names the test class that proves it; test classes end in `Test`, leak tests in `LeakTest`. Stories 2.6, 2.7 and 2.8 were flagged in readiness review as naming no test class; their specs must supply one.

## Technical Decisions

- **Module edges.** `codex` depends on `core` and on `api`; the `api` edge was added after the readiness review so the Codex can write `api`-typed JSON with a codec and a schema version, as every value crossing a module edge must. `brain` depends on `api` only and may not read files, so the Codex reaches the Brain as data loaded by the caller and handed in through `api` types, never as classes and never by the Brain itself. Nothing in `codex` may be imported by `brain`.
- **Output shape.** JSON in `codex/<tag>/`, committed and CI-checked; the Codex tables are `api` record types with a canonical encoder; the Codex carries its own version, and that version appears in the Observation header (the field exists from E1, empty until this epic decides what it holds), the Run-log header and the Registration, because the Codex determines Brain behaviour and its combat tables are measured rather than derived. No floats in hashed data; UTF-8; canonical list order so output is byte-stable.
- **Generation mechanics.** Reflection per table over the game's class lists, plus measurement for combat; the detail was deliberately deferred to the epic's stories because it carries no cross-module divergence risk. Every table records the `path:line` it was read from or the method it measured. Determinism of the generator itself is part of the seed-free guarantee: `HashMap`/`HashSet` iteration never decides output order in Shatterfish code, so sort keys or use insertion-ordered collections.
- **Layout.** `org.shatterfish.codex` holds the generators per table, the completeness check, the citation checker and the vocabulary diff; the generated docs land under the site's Codex section. The second pinned source for the diff is vanilla Pixel Dungeon (`00-Evan/pixel-dungeon-gradle`) at a tag chosen in this epic.
- **Rules versus Codex.** Mechanics rules the docs rely on live as cited rows under `docs/rules/` with a Tier and a link to the test that checks them; the citation checker keeps them honest. The Brain's own Rules index, the enumeration of claims the Brain relies on, is owned by E4, since no Brain exists yet.
- **Conventions.** Java 21, Gradle wrapper, JUnit 5, ArchUnit; `api` values are Java records; logging through `java.util.logging` with the module as logger name; the ArchUnit ban on `java.net` applies to `codex` as to every module.

## UX & Interaction Patterns

The Overlay (E5) speaks in Codex vocabulary: labels, numbers and one-line reasons use the game's own words and never imitate the game's log voice. The strings dump keyed by owning class is what makes that possible, and the asset index and journal pages exist so the instrument and the docs can name things the way the game does. Decision cards and strategy logs later quote item and mob names from these tables, so display names must be the ones the player sees, alongside the appearance-label pools for unidentified items.

## Cross-Story Dependencies

- The generator skeleton, the seed-free test and the leak test (2.1) precede every table story; each later story adds tables to the same task and extends the completeness test rather than adding a task.
- Items and decks (2.3) precede guarantees and tier tables (2.4), which reference the item catalogue; mobs (2.2) precede combat tables (2.5), which sweep mob and weapon parameters.
- The drift check and generated docs (2.9) land after the tables exist to check, and the deliberate-edit verification is done once there. The citation checker (2.10) is independent of the tables but is wired into the same upgrade procedure step that regenerates the Codex.
- The Observation header's Codex-version field (E1), the Run-log header (E3) and the Registration (E3) all carry the version this epic defines.
- The vocabulary diff (2.8) feeds the E7 variant classifier and nothing before it; the Brain's Rules index is E4's; the loader that hands Codex tables to the Brain is named in E4's first story.
- The upgrade procedure's Codex-regeneration and mechanics-diff step and its citation re-verification step both depend on this epic; the first upgrade happens after the E3 baseline.
